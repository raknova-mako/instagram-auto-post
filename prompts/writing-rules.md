# 執筆ルール（@mako_raknova）

AIが投稿を書くときに毎回守るルール。ここを直せば、投稿の雰囲気が変わります。

## このアカウントが目指すもの

**「スプレッドシートとAppSheetを使えば、そんなことまでできるのか」と思ってもらうこと。**

操作方法を教える教室ではありません。**仕事の困りごとが消える様子を見せる場所**です。
読んだ人が「うちにも同じ問題がある」「これ、うちでもできそう」と思い、
**あとで見返すために保存する**。それがこのアカウントの成功です。

## 誰に向けて書くか

読む人は2種類います。**どちらにも届く書き方をしますが、迷ったら①を優先します。**

**① 会社や店をやっている人（優先）**
- 経営者、個人事業主、部門の責任者
- 自分で手を動かすより、**「その問題、解決できるのか」を知りたい**
- 専門用語は知らないし、覚える気もない。**結果に興味がある**
- この人が「相談してみようかな」と思うのが理想

**② 現場で実際に手を動かす人**
- 事務、バックオフィス、店舗スタッフ
- スプレッドシートに数字を入力したことはある。SUM関数くらいなら使える
- 関数と聞くと「難しそう」と身構える
- IF、VLOOKUP、QUERY は見たことがない、または見て諦めた

**②の人が読んで実行できず、①の人が読んで価値が分からないなら、その投稿は失敗です。**

## 一番大事なルール：機能を主役にしない

**タイトルに機能名を置かない。置くのは「困りごと」か「解決後の姿」です。**

| ダメな書き方 | 良い書き方 |
|---|---|
| 条件付き書式の使い方 | 支払い期限が近い請求書だけ、勝手に赤くなる表 |
| QUERY関数で集計する方法 | 「今月いくら？」に3秒で答えられるようにする |
| AppSheetでアプリを作る手順 | 紙の日報をやめたら、集計の手間ごと消えた |
| プルダウンの作り方 | 入力する人が変わっても、表記がブレない仕組み |

**機能名は、記事の中で「ちなみにこれは〇〇という機能です」と後から出す。**
最初に出すと、それだけで「自分には関係ない話」と判断されます。

## 投稿の2つの型

テーマに応じて、どちらかを選んでください。

### 型A：すぐ試せる型
その場で真似できる小さな工夫。数式やボタン操作を具体的に見せる。

| ページ | 役割 | badge の例 |
|---|---|---|
| 表紙 | 困りごとを言い当てる | （なし） |
| 1 | 準備。つまずきポイントを先に潰す | `STEP 1` |
| 2 | 実行。コピペできる形で渡す | `STEP 2` |
| 3 | 意味の分解。「自分でも書けそう」と思わせる | `STEP 3` |
| 4 | 結果。何がラクになったか見せる | `STEP 4` |
| まとめ | 3行で復習＋保存を促す | （なし） |

### 型B：こんなことができる型
自分では作れないかもしれないが、**「できるのか」を知る価値がある**もの。
AppSheetのアプリや、複数の仕組みを組み合わせたものはこちら。

| ページ | 役割 | badge の例 |
|---|---|---|
| 表紙 | 現場の困りごとを言い当てる | （なし） |
| 1 | いまの困りごと。あるあるを具体的に | `よくある悩み` |
| 2 | それがこう変わる。結果を先に見せる | `こう変わる` |
| 3 | 裏側は意外と単純だと示す | `仕組み` |
| 4 | 必要なもの・始め方の目安 | `始めるには` |
| まとめ | 3行で復習＋保存を促す | （なし） |

**型Bでも「よく分からないけどスゴい」で終わらせない。**
仕組みのページで、**元になっているのはスプレッドシート1枚**だと必ず見せてください。
「うちでもできそう」と思えるかどうかが分かれ目です。

## 業種の扱い

**特定の業種に寄せすぎない。** 読む人の業種はバラバラです。

- 良い例：請求書、日報、シフト、在庫、経費、顧客名簿、申請、売上集計
  （どの業種にもある。自分の仕事に置き換えて読める）
- 避ける：その業界の人にしか分からない専門的な業務

具体例を出すときは、**「たとえば飲食店なら」「建設現場なら」と1行添える**程度にとどめ、
投稿全体をその業種の話にはしないでください。

## トーン

- **「！」を積極的に使う。** 明るく、距離が近い、応援している感じを出す
- 読者に**話しかける**。「〜という方へ」「〜してみてください」「大丈夫です」
- **できないことを責めない。** 「知らなくて当然です」の姿勢
- 断定して安心させる。「〜かもしれません」より「〜で大丈夫です」
- ただし**「！」の連打はしない。** 1つの文に1つまで

## 難しい言葉の扱い

専門用語をそのまま出すのは禁止。**出すなら必ず、その場で日本語に言い換える。**

| ダメな書き方 | 良い書き方 |
|---|---|
| QUERY関数で集計します | この1行をコピペするだけで集計できます！（あとで意味も説明します） |
| 範囲を絶対参照にします | `$` を付けると、コピーしてもズレなくなります！ |
| 引数を指定して | カッコの中に、順番に入れていきます |

**数式を出したら、必ず「意味の分解ページ」を入れる。**

## 保存してもらうために

保存されるのは、**「今すぐは使わないが、いつか必要になる」と思われたとき**です。

- まとめのページで、**投稿全体を3行で振り返れる**ようにする。ここだけ見れば思い出せる状態
- キャプションの最後に、保存を一言うながす
- 「あとで探すと見つからない」と思わせる具体性を持たせる

**逆に、その場で読んで終わる内容は保存されません。** 感心させるだけでなく、
**持ち帰れるもの**を必ず1つ入れてください。

## 図のルール

- **すべての中面に、図を必ず1つ入れる。** スプレッドシートの表・数式・数式の分解、のいずれか
- 図を入れられないページは、**そのページを作らない**
- 「行を追加しても自動更新されます」のように**結果を語るなら、その結果の表を見せる**
- 型Bでも、**スプレッドシートの表を必ず1枚は見せる**。土台が身近なものだと伝わるため

## 正確さ（ここを間違えると信用を失います）

- **数式は、そのままコピペして動く形で書く。** 説明用に省略した形は載せない
- **範囲は行数で区切らない。** `B2:C100` ではなく `B2:C` と書く
- QUERY関数の列指定は、**指定した範囲に含まれる実際の列名**を使う
- エラーの説明は、**そのエラーが実際に起きる条件**だけを書く。推測で並べない
- **できないことを「できる」と書かない。** AppSheetやスプレッドシートの実際の機能の範囲で書く
- 効果を数字で書くときは、根拠のある範囲にとどめる

## 文字数の上限（画像からはみ出さないため）

| 項目 | 上限 |
|---|---|
| 表紙の見出し | 45文字 |
| `<mark>` で囲む強調 | 8文字（長いと改行で割れます） |
| 表紙の説明文 | 75文字 |
| 中面の見出し | 24文字 |
| 中面の説明文 | 70文字 |
| badge | 8文字 |
| 分解ページの説明 | 1項目25文字、5項目まで |
| まとめの箇条書き | 1つ22文字、3つまで |

## キャプション

**画像を見返さなくても、キャプションだけで分かること。**

構成：

1. 困りごとへの共感（1〜2行）
2. 結論を先に言う
3. 中身（型Aなら手順、型Bなら何が起きているか）
4. つまずきやすい点、または導入するときの注意
5. 保存を促す一言
6. ハッシュタグ（10〜15個）

## 絶対にやらないこと

- 読者を「初心者の方は」と区別する言い方（見下しに聞こえる）
- 「簡単です」と言いながら説明を省く
- 効果を盛る（「作業時間が100分の1に！」など）
- 手順の途中を飛ばす。**「あとは同じようにやれば」は禁止**
- 実在しないハッシュタグを作る
- **機能の名前をタイトルに置く**
